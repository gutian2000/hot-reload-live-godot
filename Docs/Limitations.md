# Hot Reload Live — Limitations & Known Issues

This document lists what Hot Reload Live **does not support**, what has **minor caveats**, and what **is planned** for future versions.

---

## Hard Limitations (will crash or silently skip)

### ❌ Cannot change field layout

If you add, remove, or rename **instance fields** on any patched type, Hot Reload Live detects this via `ComputeFieldHash` and **skips the patch** with a warning:

```
[Hot Reload Live] ⚠️ Field layout changed — skipping this patch (type safety guard)
```

Why? Cross-ALC instance method forwarding works by passing the old-ALC object directly as the new-ALC type's `this` pointer. This is safe **only** if both versions have identical field offsets. If the layout differs, the new code would read/write the wrong memory.

**What to do**: Stop the game, re-run. Your field change takes effect on the next launch.

### ❌ Cannot add new types or change inheritance

Adding a brand-new class, changing `class Foo : Bar` to `class Foo : Baz`, or changing `static` → instance requires the runtime to know about the new type. Hot Reload Live's diff only matches methods that exist in **both** old and new assemblies.

**What to do**: Stop and re-run for structural changes.

### ❌ Cannot patch Godot-generated bridge methods

Methods like `SetGodotClassPropertyValue`, `Set`, `Get` (indexer accessors) are generated by Godot 4.7's source generator and marked `[CompilerGenerated]`. They are explicitly filtered out.

The one exception: these may log as "failed" in the patch count — that's expected and harmless.

### ❌ Generic methods: only covers common type arguments

Hot Reload Live patches each generic method definition for:

- `object` — covers **all reference types** (CoreCLR JIT shares code)
- `int`, `float`, `double`, `bool`, `long`, `byte`, `char`, `decimal` — common value types

If your code calls `GetGeneric<Guid>()` or `GetGeneric<MyStruct>()`, that instantiation is **not** patched. It'll run the old version until you restart.

**Rationale**: .NET 8 CoreCLR compiles each value-type generic instantiation to a unique code body. Enumerating all possible combinations is infinite. The 8 common types cover ~95% of real-world usage.

## Soft Limitations (works but caveats apply)

### ⚠️ async / iterator entry methods are skipped

Hot Reload Live **does** patch the compiler-generated `MoveNext` / `SetStateMachine` methods. But the **entry method** (e.g. `MyAsyncMethod() { await ... }`) is skipped.

Why? Harmony patching an async entry corrupts the state machine IL structure (the method body is a `stateMachine.MoveNext()` delegate setup). Skipping the entry but patching MoveNext gives you hot-reloadability on **every line after `await`** — which is where the real game logic lives anyway.

### ⚠️ Instance methods rely on identical field layout

The DynamicMethod IL stub bypasses cross-ALC type identity by **not** casting the instance. It just pushes the old object reference as the new type's `this`. This is safe only while `ComputeFieldHash` holds.

If you change **only static fields** — no problem. Static fields live on the type itself, not the instance.

### ⚠️ Harmony side effects

Hot Reload Live uses **Lib.Harmony 2.4.2**. If your game already uses Harmony directly, Hot Reload Live registers under ID `"com.gutian2000.godot.hotreload.runtime"` — there should be no conflict.

`RestoreAll()` calls `Harmony.UnpatchAll()` on this ID only.

### ⚠️ Editor-triggered reload has ~100ms latency

The editor plugin writes a marker file; the game process picks it up on the next `_Process` tick (60 FPS → ~16ms). Plus the 500ms debounce. Plus `dotnet build` (~800ms). Total end-to-end: **~1.5 seconds**.

### ⚠️ .NET 8 / CoreCLR only

This asset targets **Godot 4.7 .NET 8**. It does **not** work with:
- Godot 4.x Mono (classic) — no collectible ALC, different Harmony behavior
- Godot 3.x — different C# runtime
- GDScript — not applicable

## What IS supported (reference)

✅ All `static` method signatures (void / return / ref / out / params / overloads)  
✅ All `instance` method signatures (same as above)  
✅ Generic method bodies (for covered type arguments)  
✅ Generic class method bodies (same)  
✅ async / Task / ValueTask state machine MoveNext  
✅ iterator / IEnumerable state machine MoveNext  
✅ Field layout guard (auto-detect, auto-skip, auto-warn)  
✅ Restore All (editor menu + code)  
✅ Auto-watcher (file system events)  
✅ Manual compile trigger  
✅ Compile error surfacing (last 6 errors to console)  
✅ Memory management (old ALCs auto-unloaded, DynamicMethods rooted)

## Troubleshooting

### "Specified method is not supported" during generic patch

Harmony cannot patch open generic method definitions. If this error appears on a **user** method (not `Set`/`Get`/`SetGodotClassPropertyValue`), report it — it should be caught by our generic-enumeration filter.

### Game freezes after a save

Very rarely, a bad IL patch can corrupt the Harmony detour chain. Press **Hot Reload Live → Restore All** from the editor menu, or restart the game.

### No patches applied

1. Check that you added `AddChild(new HotReloadRuntime())` to a script's `_Ready()`
2. Check that your project has a `src/` directory (HotReloadRuntime auto-disables for exported games)
3. Check that the plugin is enabled (Project → Project Settings → Plugins)
4. Check that `Lib.Harmony` 2.4.2 is in your `.csproj` PackageReferences

### Build failed

Hot Reload Live surfaces the last 6 `error` lines from `dotnet build`. Fix them in your editor — Hot Reload Live retries on the next save.
